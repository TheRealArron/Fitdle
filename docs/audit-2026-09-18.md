## 1. CRITICAL — the opening call can be brute-forced. Six requests solve the
##    puzzle before the first guess.

`/api/call` is stateless. It refuses a second call only if the *token you send
it* already carries one:

```ts
if (session?.call !== undefined) return 409;
```

So do not send it a token. Every call with no `state` is a first call, and the
response tells you immediately whether you were right — and, when you were,
hands over the equipment hint that is supposed to arrive at guess 5.

Run live against :3000 this session:

```
today  -> {"seed":20260917,"wordLength":6,"hints":{"category":null,"equipment":null,"nextHintIn":2}}

  call Chest     -> 200  correct=false  equipmentHint=null
  call Back      -> 200  correct=false  equipmentHint=null
  call Shoulders -> 200  correct=false  equipmentHint=null
  call Arms      -> 200  correct=false  equipmentHint=null
  call Core      -> 200  correct=false  equipmentHint=null
  call Legs      -> 200  correct=true   equipmentHint="Dumbbell"

resume -> {"guesses":[],"call":{"group":"Legs","correct":true},
           "hints":{"category":null,"equipment":"Dumbbell","nextHintIn":2}}
```

Six requests. Seven is the worst case — there are seven muscle groups. The
`call:` rate limit is 20/min, so the ceiling is three full sweeps a minute.
The token from the winning sweep resumes as an ordinary, fully valid session
carrying `correct: true`, with none of the forfeit the mechanic exists to price.

**What it is worth.** Averaged over all 62 scheduled answers, against the 99-word
catalogue:

| Known | Mean candidates |
|---|---|
| length only | 19.8 |
| length + muscle group | 4.3 |
| length + group + equipment | **2.7** |

**On 27 of the 62 days that leaves exactly one candidate.** Not a hint — the
answer, at guess zero, for free. Today was one of them: Legs + Dumbbell +
6 letters, and the round ended on GOBLET.

`tests/openingCall.test.ts` has a test literally named *"calling is a genuine
risk, not a free hint"*. It passes. It tests `playGuesses`, a pure function that
is given the call as an argument, and therefore cannot see that the route hands
out unlimited attempts. This is the single clearest example in the repo of a
green test over a broken behaviour.

DECISIONS.md and the README both describe the call as "a genuine risk". As
shipped it is a free, repeatable oracle for two of the game's three metered
clues.

No stateless fix exists for an anonymous player — the client can always discard
a token — so closing this needs the server to remember the first call. That is a
design choice with a product edge to it, and it is written up in the backlog
below rather than decided here.

## 2. CRITICAL — a signed-in player who asks the guide a question before ever
##    playing gets HTTP 500 on the guess that ends their round

`fitdle_claim_ai` seeds a row for a player who has none:

```sql
insert into public.fitdle_progress (user_id, save)
values (p_user, '{}'::jsonb)
on conflict (user_id) do nothing;
```

`bankResult` then reads that row back and trusts its shape:

```ts
if (error || !data?.save) return null;   // {} is truthy, so this passes
return normalise(data.save as SaveData);
```

`normalise` only backfills the fields added after v1 — `workoutStreak`,
`drillBest` and friends. It does not create `distribution`, `played`, `wins`.
Printed this session:

```
normalise({}) -> {"workoutStreak":0,"maxWorkoutStreak":0,"workoutsDone":0,
                  "lastWorkoutSeed":null,"drillBest":0,"drillFlawless":false}
reconcile     -> TypeError: input.distribution is not iterable
```

`bankResult` has no try/catch and `/api/guess` does not wrap the call, so the
exception escapes the route handler.

Proved end to end against the live project and the live dev server, with a
throwaway account created and deleted inside the probe:

```
user bf79e233-…
fitdle_claim_ai -> ok
row.save now = {}
wordLength 6
guess 1 BRIDGE -> status=playing
guess 2 BURPEE -> status=playing
guess 3 CHINUP -> status=playing
guess 4 CRUNCH -> status=playing
guess 5 GOBLET -> HTTP 500
```

GOBLET was the answer. The player won and got a 500 instead of a reveal, a
streak, or a leaderboard place.

The flow that reaches it is not exotic: sign up → open the guide and ask how the
game works → play. The guide is deliberately available before and during a
round, which is what makes this ordinary rather than adversarial.

Three separate guarantees in the docs are false while this is live:

- progress.ts: *"a failed write must not fail the guess"* — it is not a failed
  write, it is a throw before the write, and it does fail the guess.
- README: *"Fails soft. An anonymous player, a deployment with no service-role
  key, or a failed write all fall back to the local save."*
- README: *"A cloud problem must never cost someone the result they just
  earned."*

Nothing tests `bankResult` against a row that `fitdle_claim_ai` created.
`tests/progress.test.ts` builds its inputs with `defaultSave()`, which always
has a `distribution`.

## 3. HIGH — "reset my statistics" is broken for signed-in players, and the test
##    that guards it passes

The RLS revocation took `insert` and `update` from the client. `pushCloudSave`
is an upsert. `resetProgress` → `overwriteCloudIfSignedIn` → `pushCloudSave`.

Measured against the live project, signed in as the row's own owner with the
public anon key — that is exactly what the browser holds:

```
select own row                     error=none   rows=1
UPDATE own row streak:9999         error=none   rows=0
INSERT own row                     error=42501  new row violates row-level security policy
UPSERT own row (pushCloudSave)     error=42501  new row violates row-level security policy
rpc fitdle_claim_ai                error=42501  permission denied for function
DELETE own row                     error=none   rows=1
streak column after all attempts:  1  (seeded as 1)
```

So the reset clears local storage, fails to clear the cloud, and sets
`syncState: 'error'`. The next `syncNow` merges the surviving cloud row back in
— `played`, `wins` and `maxStreak` take the max, and the streak comes from the
save with the later `lastSeed`, which is the cloud one. The reset is fully
undone.

`tests/cloudSync.test.ts` has *"a merge CANNOT express a reset - which is why
reset must overwrite"*, whose comment says in as many words: *"reset appeared to
work and was silently undone. The fix is `overwriteCloud`."* The test pins the
merge property and passes. The fix it names no longer functions.

`cloudSync.ts` says of `pushCloudSave`: *"It survives for `overwriteCloud`"*.
It does not. The last line of the same comment is the fix: DELETE is still
granted, and the probe above shows it removing the row.

## 4. HIGH — the two live checks that pass without testing anything

**`cloud:check`'s revocation probe cannot fail.** It runs:

```js
const policyProbe = await supabase              // anonymous, anon key
  .from('fitdle_progress')
  .update({ save: {} })
  .eq('user_id', '00000000-0000-0000-0000-000000000000')
  .select();
…
} else if (!policyProbe.error && (policyProbe.data ?? []).length === 0) {
  pass('client writes are revoked', 'no row was updatable');
```

and this session printed exactly that green line. But the caller is
*unauthenticated* and the row id does not exist. With the **old** `update own
progress` policy still installed, `auth.uid()` would be null, no row would match,
and PostgREST would return the same "no error, zero rows" — the same green tick.
The branch that would fail (`42501`, or a row actually updated) is unreachable
for an anonymous caller.

The check is on the one property DECISIONS.md calls out as the reason
`cloud:check` exists: *"a project running the old schema looks completely fine
while forged streaks sail through."* It would. The probe in §3 above is the
shape that works — authenticate as the row's owner and update the owner's own
existing row.

Meanwhile README line 364 claims RLS is "**verified live** by `cloud:check`
returning `42501` on an anonymous write". That 42501 comes from the *insert*
probe, which any RLS-enabled table refuses for an anonymous caller. It proves
RLS is on. It says nothing about whether the update policy was dropped.

**`check:bundle` only looks at the first occurrence of each name.**

```js
const first = text.indexOf(run[0]);
const slice = text.slice(Math.max(0, first - window), first + window);
```

The catalogue ships to the client by design, so `run[0]` is almost always
already present in an unrelated position. A real schedule leak somewhere else in
the same chunk would be measured against a 400-char window around the wrong
occurrence and reported clean.

**Demonstrated, on 2026-09-19.** The whole of `ANSWER_ORDER` was appended as a
JSON array to the built chunk that already carries the catalogue — 35 kB past
the first occurrence of the anchor, which is where the catalogue's own copy
sits:

```
planting into .next/static/chunks/0dmpsijn___dl.js
  first occurrence of SQUAT is at byte 2481 (the catalogue)
  schedule appended at byte 37248

$ npm run check:bundle
✓ no answer ordering, coaching text or video ids in any client chunk (36 files scanned)
EXIT=0
```

Every future puzzle, readable in devtools, and the guard said clean. Fixed in
iteration 6; the same planted leak now exits 1 and names the byte offset.

## 5. HIGH — roughly a quarter of the suite tests the text of the source, not
##    behaviour

`tests/helpers/source.ts` exists for good reasons and is used well in places
(asserting a secret is *not* in a file is genuinely a source question). But it
has spread. Counting call sites of `readSource`/`readCode`/`readFileSync`:

**No route handler is ever invoked by the test suite.** All six are read as
strings. The clearest case:

```ts
test('the coach route is gated on a finished round', async () => {
  const route = readFileSync(…'/api/coach/route.ts'…);
  assert.match(route, /openSession/);
  assert.match(route, /outcome\.reveal/);
```

That passes if the gate is inverted, if the session result is discarded, or if

Same shape: *"the board is read-only and rate limited"*, *"the streak board has a

claimed before the model call"*. Every one is a regex over a file.

This is why §1, §2 and §3 all shipped under a green suite. They are behaviours

## 6. MEDIUM — the extension asks for every https site and a permission it
##    never calls

`extension/manifest.json`, copied verbatim into `extension-dist/`:

```json
"permissions": ["storage"],
"host_permissions": ["https://*/*"]
```

- `grep -rn "chrome\.\|browser\.storage" src/` returns **nothing**. No
  `chrome.*` API is called anywhere. The app persists through `localStorage`,
  which needs no permission. `"storage"` is unused.
- `https://*/*` grants host access to every site on the internet. Chrome renders
  that to the user as "Read and change all your data on all websites", and it is
  the single most common reason a Web Store review stalls. What the popup
  actually needs is cross-origin `fetch` to two known origins:
  `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_SUPABASE_URL`. Both are already
  build-time constants — `build-extension.mjs` could generate the list. Image
  loads from `i.ytimg.com` do not need a host permission at all; they are
  governed by the page CSP.

The manifest is also the one artefact `npm run verify` never touches —
`build:extension` is not in the chain.

Not verified: I did not run `npm run build:extension` this session, and I have
not loaded the result in Chrome.

**Update, 2026-09-21.** Running it was the first thing iteration 8 did, and it
**failed**: adding the first route-level test in iteration 2 broke
`build:extension`, and five iterations passed without anyone knowing, because
the sentence above is true — `verify` never built it. The extension build parks
`src/app/api` aside (`output: 'export'` refuses to build with a route handler in
the tree), so `tests/openingCall.test.ts`'s `import '@/app/api/call/route'`
could not resolve and the build died on a file that is not in the extension.

Both are fixed in iteration 8: the extension build gets its own tsconfig without
`tests`, and `build:extension` is now the fourth step of `verify`. A side
benefit: `check:bundle` scans `extension-dist` as well as `.next/static`
(16 + 20 = the 36 files it reports), so the answer-leak scan now covers a
freshly built extension rather than whatever copy happened to be lying around.

## 7. MEDIUM — the guide is "safe by construction" against the app's data, and
##    safe by instruction against the model's own

`guide.ts` says:

> It is safe by construction, not by instruction … this prompt contains NO
> exercise names … It is the same principle that moved ANSWER_ORDER server-side:
> remove the capability rather than forbid the behaviour.

Verified true of the prompt — three tests grep it, and I confirmed no exercise
name appears. But the capability that matters was never in the prompt. The
guide is `claude-opus-5`, and a frontier model's own knowledge of exercise names
is a near-superset of a 99-word fitness catalogue. "Name six-letter exercises
that work the hamstrings" does not need the catalogue to be answerable.

The only thing standing between that question and an answer is this, in the
prompt:

> Do not guess, do not speculate, and do not name specific exercises even as
> examples

which is an instruction — the exact category the file says it refuses to rely
on. The structural claim is true about one attack surface and stated as though
it covers both.

`coach:probe` has four cases aimed at this and would catch a regression. But:

- It requires `ANTHROPIC_API_KEY`, which is not in `.env.local`, so it has never
  run here and is not in `verify`. **Not verified this session** — I could not
  run it.
- Its final line reports `${failures} of ${CASES.length} cases failed` while
  `failures` accumulates across both the 7 coach cases and the 7 guide cases.
  A run with 9 failures reports "9 of 7". The remediation text that follows only
  mentions the coach.
- README and DECISIONS both say the probe "fires seven adversarial prompts".
  It fires fourteen.
- The coach's `WORKAROUND` regex is a fixed phrase list. A workaround phrased
  outside it ("drop the load and keep the pattern") scores as a pass. The script

## 11. CRITICAL, found after the audit was first written — the "Today"
##     leaderboard can never contain a row

`bankResult` calls `reconcile` then `commitResult`. `reconcile` creates the
day record; `commitResult` writes `played`, `wins`, `distribution`, `streak`,
`lastSeed`, `lastResult` and `highSeed` — and never touches `save.day`. So the
row the server writes always carries `day = {seed, guesses: [], status:
'playing'}`, whatever actually happened.

Postgres derives the board's ranking columns from that blob:

```sql
day_guesses int generated always as (jsonb_array_length(save -> 'day' -> 'guesses')) stored,
day_won boolean generated always as ((save -> 'day' ->> 'status') = 'won') stored
```

Run through the real route against the live project, with a throwaway account
that had no prior row — the player wins today's puzzle in one guess:

```
guess -> 200  status=won  progress written = yes

  streak      = 1
  day_seed    = 20260917
  day_guesses = 0
  day_won     = false
  save.day    = {"seed":20260917,"status":"playing","guesses":[]}

Rows the "Today" board query returns for this seed: 0
```

`dailyBoard` filters `.eq('day_won', true)`. It is false for everyone, forever.
The partial index `where day_won` indexes nothing. The streak board is fine —
`streak` is written correctly — so half the feature works and half is dead.

This is the same shape as the two regressions the README was written around: it
is a property of the running system, invisible to every static check.
`tests/leaderboard.test.ts` asserts *"the daily board has a matching index"* and
*"ranking columns are generated from the save, not written separately"*. Both are
regexes over `schema.sql` and `leaderboard.ts`, both pass, and neither runs the
pipeline they describe.

The client used to write `save.day` as it played, which is presumably when this
last worked. The RLS revocation took that write away and the server never picked
it up.

## 12. CRITICAL — the guess history can be discarded, so a streak can never
##     break and the daily board is forgeable once §11 is fixed

The signed session is the server's only memory of the day, and the client
decides whether to send it. `POST /api/today` with no token returns a fresh
board for the same seed. Measured live:

```
burn five guesses                1..5, status=won on the fifth
POST /api/today with no token -> fresh board, 0 guesses, status=playing
win in one on the fresh board -> status=won, guesses banked = 1
```

Two consequences:

- **A streak can never break.** A player five guesses deep and wrong simply does
  not submit the sixth. They discard and restart. `commitResult` is idempotent
  per seed, but only once you *finish*, and finishing is the player's choice.
- **The daily board is forgeable.** `/api/guess` banks `guesses.length`, so a
  player who solves it in five, restarts, and re-enters the answer banks a 1.
  Inert today only because §11 means the board is empty.

README already names this exact mechanism — for the *speed* board it decided not
to build: *"anything that did would reset by discarding the session and asking
for a fresh one - so the board would rank whoever worked that out rather than
whoever solved it fastest."* The same sentence applies to guess count, and to
whether you finish at all. That was not noticed.

The two must be fixed together: fixing §11 without §12 turns a dead board into a
forgeable one.
